Project Name: CONTROLPLANE

Category: Developer Infrastructure / Feature Management Platform

Target Release: v1.0.0

Status: Architecture and Development Specification

---

# 1. PROJECT OVERVIEW

CONTROLPLANE is a developer-first, self-hostable feature management platform that allows engineering teams to control feature exposure without requiring a new application release.

A developer ships feature code inside an application but keeps the feature controlled by a remotely managed configuration.

The application uses a CONTROLPLANE SDK to retrieve and cache feature configuration.

The SDK evaluates feature flags locally.

This allows teams to:

- Enable or disable features remotely
- Release features to selected users
- Target users based on attributes
- Roll out features by percentage
- Gradually increase feature exposure
- Instantly disable problematic features
- Roll back configuration changes
- Continue operating during network failures
- Avoid releasing a new application version for configuration-only changes

CONTROLPLANE does not deploy application code.

CONTROLPLANE controls whether already-deployed application functionality should be exposed or executed.

# 2. CORE PRODUCT STATEMENT

> CONTROLPLANE is a developer-first feature delivery platform that separates feature deployment from feature release.

A feature can be:

```text
DEPLOYED

but

NOT RELEASED
```

The feature code already exists inside the user's application.

CONTROLPLANE decides:

```text
Should this feature be enabled?
```

This decision can change remotely.

---

# 3. THE CORE PROBLEM

Traditional software delivery usually follows this process:

```text
Write Code

↓

Build Application

↓

Test Application

↓

Release Application

↓

Users Receive New Version
```

This tightly couples:

```text
CODE DEPLOYMENT

and

FEATURE RELEASE
```

That creates problems.

For example:

A developer deploys a new payment system.

The code reaches production.

However, the team may not want all users to receive the new payment system immediately.

Without feature management, the developer may need to:

```text
Change Code

↓

Build Again

↓

Release Again

↓

Wait For Users To Update
```

CONTROLPLANE separates deployment from release.

The new flow becomes:

```text
Ship Feature Code

↓

Feature Disabled

↓

Enable Remotely

↓

5% Users

↓

20% Users

↓

50% Users

↓

100% Users
```

If something fails:

```text
Problem Detected

↓

Disable Feature

↓

Configuration Updates

↓

Application Changes Behavior

↓

NO NEW APPLICATION RELEASE
```

# 26. PERCENTAGE ROLLOUT

Percentage rollout allows gradual feature exposure.

Example:

```text

new_checkout

```

Approximately 25% of eligible users should receive the feature.

However, this must not be random.

A user must remain stable.

---

# 27. THE WRONG PERCENTAGE ROLLOUT

This is incorrect:

```text
Random Number

↓

If Random < 25

Enable
```

The same user could receive:

```text
Request 1

Enabled


Request 2

Disabled
```

This creates inconsistent behavior.

# 28. DETERMINISTIC PERCENTAGE ROLLOUT

CONTROLPLANE uses deterministic hashing.

Input:

```text
projectKey

+

environmentKey

+

flagKey

+

userIdentifier

+

rolloutSalt
```

Example:

```text

:

production

:

new_checkout

:

user_123

:

v1
```

This creates a canonical input.

The canonical input is hashed.

The hash produces a stable bucket.

```text
Canonical Input

↓

Hash

↓

Unsigned Integer

↓

Bucket
```

# 41. CONFIGURATION ROLLBACK

```text

v42

v43 ← Current
```

```text

```

```text

```

```text

containing

the configuration from v41
```

History becomes:

```text

v42

v43

v44 ← Restored Configuration From v41
```

History remains complete.
